Understanding 5G QoS Enforcement: Core-Network (UPF/QER) vs. RAN (E2SM-RC xApp)
================================================================================


1. NORMAL BEHAVIOR: HOW A 5G QOS FLOW'S PARAMETERS ARE NEGOTIATED
================================================================================

Before discussing enforcement, it matters where a QoS parameter like MFBR
actually comes from, because the same value is provisioned twice, on two
completely separate legs, from the same source of truth.

1.1 The QoS model (3GPP TS 23.501 S5.7)
----------------------------------------
- A UE's data connectivity is organized into PDU Sessions, each carrying one or more QoS Flows, each identified by a QoS Flow Identifier (QFI).
- Each QoS Flow is associated with a 5QI (5G QoS Identifier) - a scalar that
  indexes a standardized (or operator-defined) set of QoS characteristics:
  resource type (GBR / Non-GBR / Delay-critical GBR), Priority Level, Packet
  Delay Budget (PDB), Packet Error Rate (PER), and - for GBR flows only -
  an Averaging Window.
- For GBR QoS Flows specifically, two additional bit-rate parameters apply:
    * GFBR (Guaranteed Flow Bit Rate) - the bit rate the network guarantees
      to provide, averaged over the Averaging Window.
    * MFBR (Maximum Flow Bit Rate) - the ceiling; traffic above it "may get
      discarded or delayed by a rate shaping/policing function" (TS 23.501).
  This project's xApp (and, per the same clause, the UPF's QER, see S2 below)
  is exactly that "rate shaping/policing function" the spec is referring to.
- Two aggregate limits also exist, orthogonal to per-flow GFBR/MFBR:
  Session-AMBR (caps all Non-GBR flows of one PDU Session, combined) and
  UE-AMBR (caps all Non-GBR flows across all of a UE's PDU Sessions,
  combined). AMBR is out of scope for this project's enforcement mechanism,
  which targets per-DRB/per-flow GBR bit rates (MFBR), not the Non-GBR
  aggregate - noted here only for completeness, since both are governed by
  the same TS 23.501 S5.7 clause.

1.2 Where the value is decided, and where it is sent (the normal path)
------------------------------------------------------------------------
1. The Policy Control Function (PCF) authors a PCC (Policy and Charging
   Control) rule containing the QoS parameters for a service (TS 23.503).
2. The Session Management Function (SMF) receives this via
   Npcf_SMPolicyControl and derives two things from the same PCC rule:
     a. A QoS profile, sent to the RAN over N2 (NGAP), which the RAN turns
        into RRC/DRB configuration for the UE (TS 38.413, TS 38.331).
     b. One or more N4 rules (PDR/FAR/QER/URR, see S2), sent to the UPF over
        N4 using PFCP (TS 29.244), which the UPF turns into packet-level
        forwarding/policing behavior.
3. Both legs carry the *same* GFBR/MFBR value out from the same PCC rule -
   by design, this is meant to be one consistent QoS contract expressed
   twice, at two different enforcement points, not two independent values.

This "sent twice, from one source" property is exactly what makes the
reconciliation question in S5 meaningful: the two legs are provisioned
together, at PDU-session-establishment/modification time - but nothing
keeps them synchronized when a *third* actor changes only one of the two
legs later, at runtime. That is what a near-RT RIC control action does.


2. CORE-NETWORK-SIDE ENFORCEMENT: THE UPF AND QER
================================================================================

2.1 The N4 interface and PFCP (TS 29.244)
--------------------------------------------
The SMF controls the UPF's packet-processing behavior over the N4 interface
using the Packet Forwarding Control Protocol (PFCP). A PFCP session is built
from up to four rule types, installed via PFCP Session Establishment/
Modification Request:
  - PDR (Packet Detection Rule)   - classifies incoming packets (matches on
                                     QFI, 5-tuple, etc.)
  - FAR (Forwarding Action Rule)  - what to do with a matched packet
                                     (forward, drop, buffer, duplicate)
  - QER (QoS Enforcement Rule)    - the actual QoS treatment: rate limiting
                                     and/or gating
  - URR (Usage Reporting Rule)    - usage/charging reporting

2.2 QER fields relevant to MFBR/GFBR enforcement
----------------------------------------------------
A QER carries (among other IEs): a Gate Status (UL/DL open or closed), a
Maximum Bitrate (MBR - present when an MBR enforcement action applies to
matching packets, UL and/or DL), and a Guaranteed Bitrate (GBR - present
when a GBR has been authorized, UL and/or DL). The SMF provisions the QER's
MBR/GBR fields directly from the PCC rule's MFBR/GFBR values. QERs are
matched to traffic via the PDR they are attached to (typically keyed on QFI
for a QoS-Flow-level QER).

2.3 Enforcement point and behavior
--------------------------------------
Enforcement happens purely in the UPF's fast-path packet processing, at the
N3 (RAN<->UPF) / N6 (UPF<->Data Network) boundary - i.e. in the transport/IP
domain, on GTP-U-encapsulated packets, with **no visibility into the radio
interface whatsoever**. The UPF does not know the current CQI, MCS, PRB
availability, or scheduling contention for the UE it is policing traffic
for; it only sees byte counters and a configured rate ceiling.

2.4 Where 3GPP places the responsibility (this is the key citation)
-------------------------------------------------------------------
TS 23.501 S5.7.1.8 (AMBR and MFBR) is explicit that enforcement is **not**
solely a core-network responsibility. Per the clause (as corroborated via
secondary sources summarizing the primary spec, since direct PDF fetch was
blocked - see References):
  - MFBR is enforced in the UPF, in the Downlink, for GBR QoS Flows.
  - MFBR is enforced in the (R)AN, in both Downlink and Uplink, for GBR QoS
    Flows.
  - For non-3GPP access, the UE itself enforces MFBR in the Uplink.
  - Session-AMBR (Non-GBR aggregate) is enforced by the UPF across all
    Non-GBR QoS Flows of a PDU Session.

This is important for framing this project's work correctly in a paper:
**3GPP already anticipates dual enforcement of MFBR - UPF for DL, RAN for
DL+UL - as normal, standards-compliant behavior.** This project's RAN-side
xApp is not introducing a redundant or non-standard enforcement point; it is
implementing the *(R)AN* half of an enforcement responsibility 3GPP already
assigns, which - per this project's own investigation of srsRAN prior to
this work - existed in signaling but had no implementation, and no O-RAN
control-plane exposure, before this project (see
DRB_QOS_XAPP_SYSTEM_DESIGN.md).

2.5 Control-loop characteristics
-------------------------------------
QER installation/modification is *event-driven*, not periodic: it happens
when the SMF pushes a PFCP Session Modification in response to a PCC rule
change from the PCF (itself usually triggered by an AF request, a
subscription change, or an operator policy update). There is no defined
"real-time" timescale for this in 3GPP the way O-RAN defines one for its RIC
loops (S3.3) - it is best described as *policy-time*, and it is entirely
decoupled from instantaneous radio conditions.


3. RAN-SIDE ENFORCEMENT: THE E2SM-RC DRB QOS CONFIGURATION XAPP (THIS WORK)
================================================================================

3.1 What it is
------------------
An O-RAN E2SM-RC CONTROL Service **Style 1 ("Radio Bearer Control"), Action 1
("DRB QoS Configuration")** control action, driven by a near-RT RIC xApp,
that lets an authorized xApp update a specific DRB's negotiated 5QI/MFBR
post-admission, and have the RAN's own MAC scheduler enforce it. Full
protocol-level detail and the sequence diagram are in
DRB_QOS_XAPP_SYSTEM_DESIGN.md and sequence.txt in this same directory - this
section only summarizes what's needed for the comparison in S4.

3.2 Enforcement point and behavior
--------------------------------------
Enforcement happens in the DU's MAC scheduler, at the point where every
PDSCH (DL) / PUSCH (UL) grant is sized, per slot. This is the only point in
the entire chain - core or RAN - that has direct knowledge of instantaneous
radio conditions: channel quality (CQI), selected MCS, available PRBs, and
contention with other UEs' grants in the same slot. A rate cap enforced here
can therefore be made radio-aware in a way a UPF, operating purely on IP/GTP
packets with no radio-layer visibility, structurally cannot be.

3.3 Standards basis
-----------------------
O-RAN.WG3.E2SM-RC, CONTROL Service Style 1 ("Radio Bearer Control"), Action 1
("DRB QoS Configuration"). RAN parameters: DRB ID (key), 5QI, and a GBR-QoS-
Information container carrying MFBR (and GFBR) DL/UL - independently
corroborated against secondary sources describing the spec structure (see
References; exact RAN-Parameter-ID numbers vary across E2SM-RC versions and
should be re-verified against the specific version cited in the paper).

3.4 Control-loop characteristics
-------------------------------------
O-RAN defines the near-RT RIC's control loop budget as **10 ms to 1 s**
(O-RAN.WG1 Use Cases / Architecture Description), as distinct from the
non-RT RIC's A1-mediated policy loop, which operates on a **much larger than
1 s** timescale. An E2SM-RC Control Request falls under the near-RT budget -
several orders of magnitude faster, and crucially *event/decision driven by
radio-aware logic*, compared to the core's policy-time QER updates.


4. SIDE-BY-SIDE COMPARISON
================================================================================

| Axis                        | Core-side: UPF QER (TS 29.244)          | RAN-side: E2SM-RC xApp (this work)          |
|------------------------------|------------------------------------------|----------------------------------------------|
| Standards basis              | 3GPP TS 29.244 (PFCP), TS 23.501 S5.7.1.8 | O-RAN.WG3.E2SM-RC Style 1 / Action 1          |
| Enforcement point            | UPF (N3/N6 boundary, packet/GTP-U layer) | gNB DU MAC scheduler (PDSCH/PUSCH grant sizing) |
| Who provisions the value     | PCF -> SMF -> UPF (via PFCP)             | xApp -> near-RT RIC -> gNB CU-CP -> DU (via E2AP/E1AP/F1AP) |
| Radio-condition awareness    | None - pure packet/byte-rate policing    | Full - CQI/MCS/PRB/contention-aware at grant time |
| Directions covered by spec   | DL only (for GBR MFBR)                   | DL and UL (for GBR MFBR)                      |
| Control-loop timescale       | Policy-time (event-driven, no defined RT bound) | Near-RT: 10 ms - 1 s (O-RAN-defined)          |
| Granularity                  | Per-PDR filter (can be finer than QFI, e.g. 5-tuple) | Per-DRB (DL); per-LCG (UL, UE-controlled per TS 38.321) |
| What happens to excess traffic | Dropped/buffered/gated in the UPF's fast path, before it ever reaches the RAN | Queued/discarded inside the RAN (CU-UP/DU), since the packet already arrived over N3 |
| Vendor neutrality             | Standardized interface (N4/PFCP); UPF implementations vary | Standardized interface (E2/E2SM-RC); RAN implementations vary |
| Update trigger                | PCC rule change (AF request, subscription/policy change) | xApp decision (can be built on live RAN telemetry, e.g. per-grant data from this project's Layer 2 pipe) |


5. THE RECONCILIATION GAP
================================================================================

5.1 What the gap actually is (stated carefully)
----------------------------------------------------
Dual enforcement of MFBR (UPF for DL, RAN for DL+UL) is *not* itself a gap -
it is exactly what TS 23.501 S5.7.1.8 specifies as normal behavior (S2.4).
The gap is narrower and more specific: **when a near-RT RIC xApp changes the
RAN-side MFBR value at runtime, through E2SM-RC, there is no standardized
mechanism to propagate that change back to the UPF's QER or to the PCF's
policy record.** The two enforcement points, both legitimate under 3GPP,
silently drift out of sync the moment only one of them is updated
post-admission by a party (the near-RT RIC) that the original PCC-rule/N4
provisioning flow (S1.2) never anticipated.

5.2 Why this happens structurally, not by oversight
--------------------------------------------------------
The O-RAN near-RT RIC's only defined external interfaces are **E2** (to the
RAN: E2 Nodes / CU / DU) and **A1** (from the non-RT RIC, carrying policies
and ML model updates downward). **There is no O-RAN-defined interface from
the near-RT RIC toward the 5G Core's control plane (PCF/SMF)** at all. This
is not a missing feature of this particular xApp; it is a structural
property of the O-RAN architecture as currently specified - the near-RT RIC
was designed to control the RAN, not to coordinate with the core. Any
reconciliation would have to be built either as a new interface (outside
current O-RAN scope), or indirectly, e.g. via the non-RT RIC/A1/SMO layer
correlating RAN-side RIC actions with core-side policy over a much slower
timescale, or via an operator-specific OAM/analytics loop outside both E2
and N4.

5.3 The concrete failure mode this project actually observed
------------------------------------------------------------------
This is not a purely theoretical concern - it matches what this project
measured directly while validating the RAN-side enforcement mechanism:
when the RAN-side cap was set below the UPF/PCF's original (still-active,
never-updated) MFBR, downlink oversubscription did **not** surface as
UPF-side shaping or dropped GTP-U packets - it surfaced entirely inside the
RAN, as CU-UP/DU-side queueing and PDCP discard, because the UPF kept
forwarding at the old, higher rate it was never told had changed (see
DRB_QOS_XAPP_SYSTEM_DESIGN.md and GBR_MFBR_QOS_ENFORCEMENT.md for the full
live-validation data). In a real deployment this is a real inefficiency: the
excess data traversed N3 (consuming transport-network capacity) only to be
discarded at the RAN, when a synchronized UPF could have shaped or dropped
it earlier, at N6, before consuming any transport resources at all.

5.4 Charging/policy consistency
------------------------------------
A second, related consequence: since the RIC-driven change never reaches
the PCF, any charging (via the CHF) or policy reporting based on the PCF's
QoS records reflects the *original* MFBR, not the value the RAN is actually
enforcing. This matters for any billing model tied to guaranteed/maximum
bit rate tiers.

5.5 Framing this for a paper
---------------------------------
This gap is best framed as an **open research/standardization question**
this project surfaces rather than solves: RAN-side, radio-aware QoS
enforcement via E2SM-RC is a genuine, standards-anticipated capability this
project newly implements and validates - but a *complete* system would need
a defined (currently non-existent) mechanism to keep near-RT-RIC-driven
RAN-side overrides consistent with the core's QER/policy state, likely via
either an extension to the non-RT RIC/A1/SMO coordination layer, or a new,
currently unstandardized RAN-to-core feedback path. Proposing and
evaluating such a mechanism is a reasonable direction for future work / a
follow-on contribution.


6. CONCLUSION
================================================================================
Core-side (UPF/QER) and RAN-side (E2SM-RC xApp) MFBR enforcement are not
competing approaches - 3GPP explicitly assigns both a role, at different
points in the DL path and, for UL, exclusively to the RAN. This project
implements and live-validates the RAN-side half of that standards-defined
responsibility, exposed through the standard O-RAN control surface for it,
where before this work srsRAN carried the necessary QoS state end-to-end but
never actually enforced or exposed it for RIC control. What is genuinely
missing - in the O-RAN architecture generally, not in this implementation
specifically - is a standardized way to keep that RAN-side, near-real-time
override consistent with the core's own, independently-provisioned view of
the same QoS contract.
