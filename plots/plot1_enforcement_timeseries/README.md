# Plot 1 — Per-DRB UL MFBR enforcement time series

## What it shows

Three figures — `plot1_2mbps`, `plot1_4mbps`, `plot1_6mbps` — one per cap level in a single UL MFBR cap
staircase (2 → 4 → 6 Mbps) applied to the same DRB via the xApp (E2SM-RC Style 1 / Action 1
`RICControlRequest`). Each figure shows that cap's full before → during → after window: the uncapped phase
immediately preceding it, the 45s cap-active phase itself, and the uncapped phase immediately following it (the
"before"/"after" of adjacent caps are shared between neighboring figures, since the staircase runs
back-to-back in one session). No titles are included in the figures themselves — use the file name / a caption
to identify which cap level each one shows.

Each figure ships with a matching `_caption.txt` (e.g. `plot1_2mbps_caption.txt`) — a paper-style caption with
summary statistics (mean offered/delivered rate, recovery time after cap removal) computed directly from the
data, ready to drop under the figure in a document.

Each figure plots UL throughput over time at two points simultaneously:

- **Offered load** (green, dashed): UDP traffic generated by the UE-side `iperf3` client, held constant at ~10 Mbps throughout.
- **Delivered throughput** (blue, solid): what actually arrives at the core-side `iperf3` server — i.e. what got through the RAN.

The shaded region marks the cap-active window; the red dashed line is that phase's configured cap value.

## What it demonstrates

- **Enforcement**: delivered throughput converges to each configured cap within a few seconds of it being applied — ~1.8 Mbps at the 2 Mbps cap, ~3.6 Mbps at 4 Mbps, ~5.5 Mbps at 6 Mbps (the small gap below each target is expected protocol/segmentation overhead).
- **Clean recovery between phases**: after each cap is removed, delivered throughput returns to the full ~9–10 Mbps offered rate within about two seconds — no lingering restriction, no crash, no dropped connection, and this holds across all three consecutive cap changes in the same UE session.
- **No unnecessary signaling**: this run used the fully-fixed gNB build (see below) — the whole apply→enforce→remove→recover cycle, repeated three times, produced exactly one over-the-air RRCReconfiguration message in total (the very first one, from initial UE attach), none for any of the MFBR changes themselves, consistent with the "signal only deltas" principle (TS 38.331 §5.3.5.6.1/5.3.5.6.5).

## The transient dip (~5s near-zero right after the first cap application)

Delivered throughput briefly drops close to zero for a few seconds immediately after the first cap is applied, before settling at the steady enforced level. This is a genuine transient, not a plotting artifact — most likely the token-bucket rate limiter starting from a full bucket at the pre-existing (uncapped, ~10 Mbps) sending rate and draining the backlog that had already built up in the RAN before the new, much lower budget takes over steady-state. Later phases in the same run don't show this as sharply since the bucket is already partially drained from the prior phase.

## Data provenance

- `data/iperf_server.log`, `data/iperf_ul.json` — iperf3 JSON reports (`--logfile`), core-side and UE-side respectively. Both files accumulate one JSON document per test run across this investigation's several redeploy-and-retest cycles; `generate_plot.py` selects the document matching this run's recorded start time.
- `data/xapp_events.log` — stdout of `ul_mfbr_test_xapp.py`, giving wall-clock timestamps for each RIC Control Request.
- `data/test_timing.txt` — epoch anchor for this specific run.
- `data/combined_timeseries.csv` — merged, epoch-aligned output used to build the plot.

## Why the full 2/4/6 Mbps staircase is now plotted (previously only 2 Mbps was)

An earlier run of this same test crashed partway through the 4000/6000 kbps phases. Root cause (found and fixed
since): a standing gNB QoS-config gap (`poll-pdu`/`poll-byte` both disabled) combined with sustained
MFBR-clamped backpressure left RLC AM's `t-PollRetransmit` with no path to re-arm once the TX SDU queue stopped
emptying, per TS 38.322 §5.3.3.2 - full root-cause writeup in
`agentic_ran/UL_MFBR_ENFORCEMENT_STATUS.md` §7. Fixed by setting `poll-byte: 25000` in `gnb_zmq.yaml`. This
plot's data is from a clean re-run of the full staircase after that fix, with zero crashes across all three
cap phases.

## Reproducing

```bash
python3 generate_plot.py
```

Regenerates `plot1_{2,4,6}mbps.{png,pdf}`, `plot1_{2,4,6}mbps_caption.txt`, and
`data/combined_timeseries.csv` (the full-session merged dataset, all three cap phases) from the raw data files.
